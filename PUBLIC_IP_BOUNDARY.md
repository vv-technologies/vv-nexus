# Public IP Boundary

This file explains how to read the public intellectual boundary of `vv-nexus`.

Its purpose is not to overclaim.
Its purpose is to distinguish:

- what is being shared publicly
- what is being documented as invention logic
- what remains implementation detail
- what should still be treated as internal or evolving

## Core Principle

Public visibility does not mean public domain.

Material in this repository may serve different roles at the same time:

- product surface
- implementation artifact
- invention record
- founder architecture note
- ecosystem positioning layer

## What This Repository Publicly Exposes

`vv-nexus` publicly exposes parts of:

- the VV ecosystem model
- LEA-facing web surfaces
- VNEX-facing web surfaces
- VV Pulse-facing pages
- the founder's system architecture direction
- selected invention-linked documents

This public exposure should be read as:

- evidence of system development
- evidence of ecosystem structure
- evidence of framework and product thinking

It should not be simplified into "only a landing page repo" or "only loose notes."

## Boundary Between Framework And Product

The clean reading is:

### Framework Layer

The invention and framework layer includes ideas such as:

- VVhi
- the VV language structure
- personal shelves
- unique-per-human LEA logic
- ecosystem-level orchestration logic
- field-truth plus intelligence combination

These should be read primarily as:

- system logic
- framework logic
- invention direction

### Product Layer

The product layer includes visible surfaces such as:

- LEA pages
- VNEX pages
- VV Pulse pages
- ecosystem-facing interfaces

These should be read primarily as:

- implementation surfaces
- product experiments
- user-facing or founder-facing interfaces

## Boundary Between Public And Internal

Some material is public because it helps explain the system.
That does not mean every internal rule, method, or long-term implementation detail is fully disclosed.

The practical rule is:

- public enough to establish direction, identity, and structure
- selective enough to preserve internal depth and future separation

## Founder Logic And Public Record

Certain documents matter because they establish:

- origin logic
- naming logic
- system relationships
- invention continuity

This is why documents such as:

- [`VV_INVENTIONS_INDEX.md`](./VV_INVENTIONS_INDEX.md)
- [`VV_LANGUAGE_SPEC.md`](./VV_LANGUAGE_SPEC.md)
- [`VV_ECOSYSTEM_MODEL.md`](./VV_ECOSYSTEM_MODEL.md)

should be read as public record and structure documents, not only as casual notes.

## What Should Not Be Assumed

From public repo visibility alone, no reader should assume that:

- every visible concept is fully shipped
- every visible structure is the final commercial structure
- every internal implementation detail has been fully disclosed
- mirrored or transitional folders are separate canonical products

For LEA source truth, use [`LEA_SOURCE_MAP.md`](./LEA_SOURCE_MAP.md).
For repository state, use [`STATUS.md`](./STATUS.md).

## Practical Interpretation

The safest and most accurate public interpretation is:

- `vv-nexus` shows real ecosystem development
- it documents parts of the product layer and the system layer
- it contributes to the public record of the VV framework direction
- it still contains internal, transitional, and evolving material

## Summary

The public IP boundary of `vv-nexus` is:

- open enough to establish authorship, direction, and seriousness
- controlled enough to distinguish framework from interface
- structured enough to separate active product surfaces from deeper invention logic
