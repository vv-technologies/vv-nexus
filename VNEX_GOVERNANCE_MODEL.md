# VNEX Governance Model

This document defines how VNEX should be governed as a platform.

Its purpose is to avoid two weak extremes:

- a fully chaotic platform with no real control
- a platform that depends manually on the founder for every decision

VNEX should instead be governed as a controlled platform with creator ownership, platform rules, and auditable moderation.

## Core Principle

VNEX should be:

- centralized in governance
- flexible in participation
- controlled in access
- creator-respecting in ownership

This means the platform itself sets the rules of operation, while creators retain control over their own works and visibility choices.

## One Account, Multiple Roles

VNEX should not force users into separate account types.

The correct model is:

- one account
- multiple roles by behavior

A person may be:

- a creator in one context
- an explorer in another
- a tester in one project
- a space owner in another

The platform should separate:

- identity
- role
- permissions
- access history

not the user into disconnected account systems.

## Governance Layers

### Platform Governance

This is the centralized layer.

The platform governs:

- account rules
- access systems
- moderation systems
- reporting systems
- safety systems
- payments
- enforcement actions
- audit logs

This layer belongs to VNEX as a platform, not to any one creator.

### Space Governance

This is the creator-controlled layer.

Each creator or team space should be able to govern:

- what they publish
- what remains private
- what becomes hybrid
- who can request access
- who is accepted into testing
- how previews are shown
- how feedback is received

This layer belongs to the creator or space owner, within platform rules.

### Work Governance

Each work should also have its own local control settings.

These include:

- visibility state
- access type
- preview depth
- participation rules
- testing scope
- release state

This prevents the whole platform from becoming all-or-nothing.

## Role-Based Permissions

VNEX should run on permissions, not only labels.

Examples:

- a creator can publish and configure access
- an explorer can browse and request access
- a tester can enter approved testing areas
- a collaborator can gain expanded access within a work
- a suspended user can lose access without deleting the entire system structure

The product should always know:

- who the user is
- what role they are acting in
- what they are allowed to see
- what they are allowed to do

## Trust And Safety Model

VNEX should not assume that all users act in good faith.

The platform should therefore include:

- reporting flows
- moderation review
- access logs
- anti-abuse rules
- repeat offender controls
- takedown paths
- suspension and removal powers

Trust should be earned over time through:

- useful participation
- clean history
- accepted access behavior
- creator trust
- platform compliance

## Centralized And Decentralized At The Same Time

VNEX should not pretend to be fully decentralized if the platform is making real platform decisions.

The honest and useful model is:

### Centralized

- rules
- moderation
- identity system
- payments
- reports
- sanctions
- legal handling
- platform standards

### Decentralized In Practice

- creators own their works
- spaces control their own visibility
- access decisions can happen at project level
- not every work must become public
- not every asset must be stored or exposed the same way

This gives platform order without killing creator control.

## Founder Independence

The platform must not be described as depending personally on the founder for every conflict or access decision.

Instead, VNEX should be structured around:

- platform policies
- moderation process
- reporting channels
- review standards
- enforcement actions

This protects the founder, the company, and the long-term seriousness of the platform.

## Official Governance Rule

Every VNEX feature should pass this test:

- does the platform keep rule authority?
- does the creator keep work control?
- does the user understand what is visible and why?
- can decisions be logged, reviewed, and enforced?

If not, governance is too weak.

## Summary

VNEX should be governed as:

- one platform
- many spaces
- many works
- role-based permissions
- centralized platform rules
- creator-level visibility control
- auditable moderation and enforcement
