# VNEX MVP Structure

This document defines the first real product structure VNEX should be built around.

Its purpose is to keep the platform:

- premium
- narrow enough to ship
- broad enough to support more than software
- aligned with the creator and explorer model

## Core MVP Principle

The VNEX MVP should not try to be everything at once.

It should prove one strong product loop:

- a creator brings a work into VNEX
- the work becomes visible in a controlled way
- an explorer discovers it
- the explorer requests or receives access
- the creator gets feedback, testing, or early audience

If this loop works, the platform has a real base.

## MVP Goal

The MVP goal is not "build the full universe."

The MVP goal is:

- make controlled visibility feel real
- make hybrid access feel useful
- make early participation feel premium

## The Three Core Actions

The first VNEX should revolve around three primary actions:

1. `Create a work`
2. `Control visibility`
3. `Open access`

Everything else is secondary.

## The Two Main User Modes

The MVP should serve:

- `Creator mode`
- `Explorer mode`

But through one account system, not two separate products.

### Creator Mode

The creator enters VNEX to:

- create a space
- add a work
- choose visibility
- post updates
- request feedback or testers
- open access

### Explorer Mode

The explorer enters VNEX to:

- discover works
- filter by category or need
- open previews
- request access
- follow works
- leave feedback where allowed

## Core Product Objects

The MVP should be built around a small number of clear objects.

### 1. Space

The space is the user's main identity area inside VNEX.

It contains:

- profile
- summary
- list of works
- access reputation over time

### 2. Work

The work is the core unit of the platform.

A work may be:

- product
- AI tool
- music release
- game
- media piece
- research experiment
- hybrid project

Each work should contain:

- title
- type
- short summary
- visibility state
- stage
- need
- preview
- updates

### 3. Update

An update is how a work stays alive.

An update may contain:

- text progress
- image
- video
- audio
- link
- build note
- release note
- blocker note

### 4. Access Request

This is how the platform moves from passive viewing to meaningful participation.

An access request may be for:

- testing
- feedback
- preview entry
- early access
- collaborator entry

## Core States

Each work should have a simple stage system.

Recommended MVP stages:

1. `Draft`
2. `In Progress`
3. `Testing`
4. `Open Access`
5. `Released`
6. `Archived`

This gives structure without overload.

## Core Visibility System

The MVP must keep the three-state model.

### Private

Visible only to the creator and approved internal users.

### Hybrid

Visible publicly in a controlled form, with optional access request or limited preview.

### Public

Openly visible and intentionally released.

## Core Needs System

The MVP should let the creator attach one main need to a work.

Recommended needs:

- `Feedback`
- `Testers`
- `Early Access`
- `Collaborators`
- `Listeners`
- `Nothing Open Right Now`

This makes discovery more useful than a generic feed.

## MVP Navigation

The platform should remain minimal.

Recommended top-level structure:

1. `Home`
2. `Works`
3. `Access`
4. `My Space`

Optional later:

- `Notifications`
- `Saved`
- `Settings`

## MVP Home

The home surface should not be a chaotic social timeline.

It should show structured discovery blocks such as:

- `Now Opening`
- `In Progress`
- `Need Testers`
- `New Hybrid Works`
- `Fresh Releases`

This helps explorers understand the platform quickly.

## MVP Work Page

Every work should have a premium page with:

- title
- creator
- category
- stage
- visibility
- one-line summary
- need
- preview area
- updates
- access action

This page is the heart of the product.

## MVP Space Page

Every creator should have a space page with:

- name
- short profile
- category focus
- works list
- selected status markers
- optional access reputation later

This makes VNEX feel like a platform, not just isolated posts.

## MVP Creator Flow

The first creator flow should be:

1. create space
2. create first work
3. choose type
4. choose stage
5. choose visibility
6. add preview
7. choose one need
8. publish work page
9. add updates over time

This is enough for a real first launch.

## MVP Explorer Flow

The first explorer flow should be:

1. land on Home or Works
2. discover a work
3. open work page
4. understand what it is
5. preview it
6. request or enter access
7. follow the work
8. leave feedback if allowed

If this flow feels premium, the product is working.

## MVP Monetization Fit

This structure matches the V1 monetization model naturally.

### Free

- one space
- limited works
- basic previews
- basic access requests

### Creator Pro

- more works
- better access tooling
- richer previews
- better release control

### Paid Access Later

- selected works can add paid access flows later

### Explorer Premium Later

- better discovery, better alerts, better access signals later

## What To Exclude From MVP

To keep VNEX premium and shippable, exclude these from the first serious version:

- full social chat
- complex internal messaging
- gamification
- token systems
- ad systems
- large dashboard sprawl
- too many tabs
- creator marketplace complexity
- revenue sharing complexity

These can come later if the core loop proves itself.

## MVP Success Test

The MVP should be considered successful if:

- a creator can publish a work cleanly
- an explorer can discover and understand it quickly
- access can be requested or opened smoothly
- the creator gets real response
- the product feels controlled and premium, not noisy

## Summary

The VNEX MVP should be:

- one account
- creator and explorer compatible
- work-centered
- visibility-centered
- access-centered
- minimal in navigation
- premium in presentation

That is the correct first structure to build.
